# Solution Scope – समाधान का दायरा

## Multi-Project Workspace और Access Control

### मल्टी-प्रोजेक्ट वर्कस्पेस और एक्सेस कंट्रोल

**PM-01 Project Portfolio – प्रोजेक्ट पोर्टफोलियो**
एक साथ कई projects बनाने और manage करने की सुविधा होनी चाहिए। प्रत्येक project के लिए अलग-अलग owner, team, budget, schedule और records होने चाहिए।

**PM-02 User Assignment – यूज़र असाइनमेंट**
प्रत्येक user को एक या एक से अधिक projects में assign किया जा सके। Default रूप से user को उन projects के अलावा किसी अन्य project को देखने की अनुमति नहीं होनी चाहिए जिनमें उसे assign किया गया है।

**PM-03 Granular Permissions – विस्तृत Permissions**
User setup करते समय administrator को project और module के आधार पर **View** या **Edit** rights देने की सुविधा होनी चाहिए। जहाँ sensitive financial या commercial data हो, वहाँ आवश्यकता के अनुसार **field-level restrictions** भी लगाए जा सकें।

**PM-04 External Access – बाहरी Access**
Project owners और approved third parties के लिए controlled access उपलब्ध होना चाहिए। उन्हें केवल वही projects और information दिखाई देनी चाहिए जिनके लिए उन्हें explicitly authorization दिया गया है।

**PM-05 Auditability – Audit Trail**
महत्वपूर्ण **Create, Update, Import, Approval, Permission और Report Generation** जैसी सभी activities का record रखा जाना चाहिए, जिसमें user और timestamp की जानकारी हो।

# Project Setup, Budgets और Cost Centers

## Project Setup, Budget और Cost Center Management

**PM-06 Project Profile – Project की जानकारी**
प्रत्येक project में निम्न जानकारी capture की जानी चाहिए:

* Project Name
* Project Code
* Project Owner
* Internal Team
* Client / Sponsor
* Start Date
* Target Completion Date
* Status
* Currency
* Relevant Notes
* Attachments

### Project Hierarchy

**Resort बनाया जाएगा।**

Resort के अंदर:

```text
Resort
   ↓
Parent Project
   ↓
Sub-Projects
```

हर **Sub-Project को एक अलग project** माना जाएगा।

Parent Project के उदाहरण:

* MEP
* Civil
* New Development
* Major Renovation
* अन्य project types

इन Parent Project types को system में **Add / Delete / Modify** करने की सुविधा होनी चाहिए।

---

## PM-07 Budget Baseline – Budget तय करना

प्रत्येक project के लिए एक approved budget निर्धारित किया जाना चाहिए और उस budget को आवश्यकता के अनुसार अलग-अलग **Cost Centers (CC)** में distribute किया जा सके।

यदि **Project A एक Parent Project** है और उसके अंदर Sub-Projects हैं, तो Sub-Projects का budget अलग-अलग Cost Centers में assign किया जाना चाहिए।

इस स्थिति में:

```text
Parent Project
       ↓
Sub-Project 1 → Cost Center 1
Sub-Project 2 → Cost Center 2
Sub-Project 3 → Cost Center 3
```

इन Sub-Projects को Parent Project के लिए **Cost Centers** के रूप में माना जाएगा।

यदि किसी Cost Center का **80% allocated budget खर्च हो जाता है**, तो system में budget के लिए **R-A-G (Red-Amber-Green) status/flag** दिखाई देना चाहिए।

### R-A-G Status और Email Alert

R-A-G status के अनुसार **Escalation Matrix** के आधार पर email trigger होना चाहिए।

---

## PM-08 Budget Versions – Budget Version Management

Approved baseline budget को सुरक्षित रखा जाना चाहिए।

यदि budget में कोई authorized revision किया जाता है, तो system को निम्न जानकारी maintain करनी चाहिए:

* Revised Budget
* Revision का कारण
* Revision Date
* Approver
* Previous Budget Version
* Current Approved Version

इससे सभी budget revisions का historical record उपलब्ध रहेगा।

---

## PM-09 Financial Roll-up – Financial Summary

System में Cost Center और Project level पर financial summary दिखाई जानी चाहिए।

जहाँ source data उपलब्ध हो, वहाँ निम्न जानकारी दिखाई जाए:

* Budget
* Current Commitment / Purchase Cost
* Actual Spend
* Forecast
* Variance

यह information अलग-अलग Cost Centers से लेकर पूरे Project तक roll-up होनी चाहिए।

# BOQ और Item Pricing

## PM-10 Standard BOQ Import – BOQ Import

एक agreed Excel template के माध्यम से पूरी **Bill of Quantities (BOQ)** को बिना line-by-line data entry के import करने की सुविधा होनी चाहिए।

**लेकिन requirement के अनुसार system को केवल एक fixed/standard Excel template पर depend नहीं करना चाहिए।**

क्योंकि BOQ file **third-party sources से प्राप्त होती है**, इसलिए system में अलग-अलग formats की Excel files को handle करने की flexibility होनी चाहिए।

अर्थात:

> System को third-party से आने वाली BOQ files के लिए flexible import mechanism प्रदान करना चाहिए, ताकि हर बार एक fixed standard Excel format की आवश्यकता न हो।

---

## PM-11 Import Validation – Import Validation

BOQ import करते समय system को data validate करना चाहिए, जैसे:

* Required columns
* Item Codes
* Units
* Quantities
* Prices
* Total Amount
* Duplicate Items
* Malformed / Invalid Rows

यदि कोई error हो तो data commit करने से पहले user को **downloadable error report** उपलब्ध होनी चाहिए।

---

## PM-12 Item and Price Master – Item Database

एक बड़ी reusable **Item / Price Master Database** maintain की जानी चाहिए।

प्रत्येक item में निम्न जानकारी होनी चाहिए:

* Item
* Unit
* Purchase Price
* Description
* Image
* Brand
* Item Code
* Standard Price
* Effective Date
* Source
* Category (Optional)

इस database को future projects में दोबारा उपयोग किया जा सके।

# Main Task और Sub-Task Management

एक **Main Task** के अंदर multiple **Sub-Tasks** बनाए जा सकें।

हर दिन Sub-Task की progress update करनी होगी।

### Daily Sub-Task Update

Site team को daily basis पर निम्न information update करने की सुविधा होनी चाहिए:

* **% Completion**
* **Status Dropdown**
* **Text Field** – Optional
* **Attachment Upload**
* **Remark**

यदि `% Completion` को change करना है, तो यह केवल **Task Owner** ही कर सके।

### Site Team Remarks

Site team को **Remark** field में निम्न जानकारी लिखने की सुविधा होनी चाहिए:

* Delay का reason
* Site issue
* Other relevant information

### Excel Status Upload

Site team को standard Excel file के माध्यम से अपना daily status application में upload करने की सुविधा होनी चाहिए।

# PM-30 Project Completion Report / Handover Report

Project complete होने पर **Project Completion Report / Handover Report** generate की जानी चाहिए।

Project Summary Report का sample **Saji द्वारा share किया जाएगा।**

### Project Closure

Project को close करने के लिए **Project Completion Report पर signature होना और signed report को upload करना mandatory** होना चाहिए।

केवल **Project Manager** को project close करने की permission होनी चाहिए।

### Leftover Inventory

Project close करने से पहले:

> **Left Over Inventory को update करना mandatory होना चाहिए।**

जब तक leftover inventory update नहीं होती, project close नहीं किया जा सके।

# Incident / Issue Tracker

System में एक अलग **Incident / Issue Tracker Module** भी होना चाहिए।

हर incident/issue के लिए निम्न information capture की जाए:

* **What is the issue?** – समस्या क्या है?
* **Where is the issue?** – समस्या कहाँ हुई?
* **When did it happen?** – समस्या कब हुई?
* **Reported By** – समस्या किसने report की?
* **Impact** – समस्या का impact क्या है?
* **Priority** – Priority क्या है?

### High-Priority Issue Notification

यदि कोई issue **High Priority** का है, तो system को सभी संबंधित **High-Priority Stakeholders** को email notification भेजनी चाहिए।

```text
Incident / Issue
       ↓
Issue Details
       ↓
Priority
       ↓
High Priority?
    ↓       ↓
   YES      NO
    ↓
Email to High-Priority
Stakeholders
```
